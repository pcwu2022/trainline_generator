The algorithm

The browser runs the existing incremental Python optimizer in your browser. It starts with an empty network, evaluates possible edits, and retains an evolving network. It searches a limited candidate graph; it does not guarantee a global optimum.

  1. Prepare geography offline. Filter cities, estimate population catchments, and calculate terrain-priced conventional and high-speed routes. Save those routes, their construction costs, and a display map as compact files.
  2. Propose edits. Sample network changes and add demand-driven connection proposals. Evaluate infrastructure, services, transfers, frequency, passenger demand, capacity and annual finances.
  3. Compare and repair. Check budget, subsidy, spill and infrastructure capacity constraints. The search can repair capacity or connectivity and accept compatible edits together.
  4. Update the network. Favor ridership and coverage early, then give finances more weight as need satisfaction increases. Later iterations can integrate and consolidate the network. Stream the current result to the map.

The first three minimized objectives are annual net cost, negative passenger trips, and negative served catchment population:

J = w₁ × (annual cost − revenue) / S₁
− w₂ × annual trips / S₂
− w₃ × served population / S₃

S₁ is search.finance_scale_eur, S₂ is the total fixed reference trips, and S₃ is the total capturable population; each scale is at least 1. This score is used alongside phase-specific acceptance rules and constraints.

Profile

A profile selects a region’s bounding box, country filter, population inputs, and other defaults. Selecting Taiwan, for example, loads Taiwanese cities and prepared Taiwanese terrain routes. Changing profiles loads that profile’s default settings and clears the previous result.

The website only offers profiles with prepared bundles. The map image is a visual background; numerical alignments and terrain costs in the graph drive the optimization. The original elevation raster is used during offline preparation and is never downloaded by the website.

Regional profiles

Spain, Italy, Poland, Switzerland and India select their country’s cities. Benelux combines Belgium, the Netherlands and Luxembourg. Scandinavia combines Denmark, Norway and Sweden. India uses the Asia population input; the European profiles use the Europe population input.

The northeastern United States profile uses Connecticut, Maine, Massachusetts, New Hampshire, Rhode Island, Vermont, New Jersey, New York and Pennsylvania. City coordinates and population-cell centroids are selected using official state polygons, rather than only a bounding rectangle. This follows the US Census Northeast region.

Number of cities

prep.max_cities limits the retained cities. Candidates are filtered by region, country and minimum population, then ordered by descending population. Smaller city centers inside an already retained metropolitan catchment are skipped.

catchment radius (km) = center_coefficient × √(local population density)
effective population Pᵢ* = city population Pᵢ × capture multiplier κᵢ

Population samples are assigned exclusively to their nearest station within its radius. The capture multiplier includes prep.uptake; it can exceed 1 when the catchment population exceeds the city-proper population. Local H3 density is smoothed with 40% from the center cell and 10% from each of its six neighbors.

Each website limit—4, 8, 12, 20, 50 or 100—loads a separately prepared graph, including its own catchment allocation. These are maximum counts: a profile may retain fewer eligible cities after population and metropolitan-catchment filtering. The selector shows the actual available count when it is below the limit. Cities are never duplicated to reach a target. More cities create more markets and candidate connections, generally increasing runtime. Changing city count preserves your other editable settings. More cities do not guarantee more profit or a better network.

Iterations

search.generations is the maximum number of incremental network updates. Each update can evaluate many designs and accept several compatible changes, so it is not a count of routes or individual evaluations.

More iterations allow additional exploration. The run can stop early when the neighborhood is exhausted or the time limit is reached. The setting also affects when the search transitions from growth toward integration and consolidation, so changing it can change the early trajectory too.

Proposals per update

search.population controls how many pending neighboring designs are randomly sampled without replacement, using proposal weights. With N pending proposals and setting p, the sampled count is min(p, N). The minimum allowed setting is 4.

Demand-driven connection packages are then added deterministically if they were not already sampled. Repairs and compatible batches can add more evaluations. This is why the displayed evaluation count can exceed proposals × iterations. A larger setting broadens exploration per update and usually costs more CPU time.

Random seed

search.seed initializes NumPy’s random generator for proposal sampling and any enabled annealing. It must be a nonnegative integer.

Use the same seed, graph, configuration and runtime to reproduce the random choices. Try several seeds to see how much a result depends on the search path. A wall-clock time limit can reduce reproducibility because different devices complete different amounts of work.

Time limit

search.time_limit_seconds limits the search time. Set it to 0 to disable this limit. It excludes Python startup, package downloads and prepared-file loading.

The code checks elapsed time between search operations; one synchronous evaluation can finish after the requested deadline. The Stop button immediately terminates the worker and retains the last displayed update.

Demand multiplier (k)

demand.k scales the gravity market between each pair of cities:

Mᵢⱼ = k × (Pᵢ*)ᵃ × (Pⱼ*)ᵃ / max(dᵢⱼ, d_min)ᵝ
Q_ref,ᵢⱼ = 2 × Mᵢⱼ

Pᵢ* and Pⱼ* are effective catchment populations; a is demand.a; dᵢⱼ is great-circle distance in km; d_min is minimum_distance_km. Pairs beyond maximum_distance_km have zero demand, and a city has no trips to itself. The factor 2 counts both directions.

Doubling k doubles the fixed reference market at unchanged geography. Actual carried trips may grow less because capacity, service and the selected network also change. Setting k to 0 removes all modeled passenger demand. k is a model calibration parameter, not a percentage.

Journey-time response

The default reference_elasticity model adjusts the reference market according to the network’s fare-free journey time:

T_ref = access at both ends + d × reference_detour_ratio / reference_speed
+ reference_wait_hours + reference_transfer_hours
T = access at both ends + in-vehicle time + boarding waits
+ number of transfers × transfer_hours
Q_potential = Q_ref × (T / T_ref)^total_elasticity
Q_shifted = Q_ref × (T / T_ref)^shift_elasticity

Each boarding has expected wait 0.5 / frequency hours. Faster journeys increase demand because the elasticities are negative. For example, at total elasticity −1.4, reducing journey time to 80% of its reference gives 0.8^(−1.4) ≈ 1.37 times the reference demand before capacity limits. Disconnected journeys have zero demand. The reported shift change is Q_shifted − Q_ref, and induced change is Q_potential − Q_shifted.

Distance decay (beta)

demand.beta is β in the gravity formula above. It controls how strongly distance suppresses the baseline market. At equal populations and distances above the floor, a pair twice as far away has 2^(−β) times the market.

With β = 1.2, that ratio is about 0.435. Larger β favors nearby city pairs more strongly and also changes the overall demand scale for distances measured in km. β does not change routing geometry or train speed.

Upfront budget

constraints.upfront_budget_eur limits initial capital:

C_upfront = track capital + station capital + fleet capital
budget constraint = C_upfront / B − 1 ≤ 0, when B > 0

The website accepts € million and multiplies the entered value by 1,000,000. Entering 250 means €250 million. A value of 0 disables this constraint. It does not mean a zero construction budget. A low positive budget can prevent expansion.

Maximum annual subsidy

constraints.maximum_subsidy_eur limits the annual deficit, including annualized capital:

net = revenue − total annual cost
subsidy constraint = −net / S − 1 ≤ 0, when S > 0
equivalently: net ≥ −S

The input is in € million per year. Setting 50 permits an annual deficit up to €50 million under this constraint. Setting 0 disables the subsidy constraint; it does not require a balanced budget. Annual net already includes annualized infrastructure and fleet costs, so it is broader than an operating cash deficit.

Discount rate

finance.discount_rate converts capital to an equivalent yearly charge using an asset’s configured lifetime n:

CRF(r, n) = r / [1 − (1 + r)^(−n)] for r > 0
CRF(0, n) = 1 / n
annual capital = C_track × CRF(r, n_track)
+ C_station × CRF(r, n_station)
+ C_fleet × CRF(r, n_fleet)

The website accepts percent: enter 4 for r = 0.04. At 4% over 50 years, €1 billion of track capital has an annual capital charge of about €46.6 million. At 0%, that charge is €20 million. A higher rate generally makes capital-intensive designs less attractive without changing their upfront construction price.

Operating hours per day

operations.hours_per_day combines with days_per_year:

H = operating hours per day × operating days per year
annual train-km for one service = 2 × frequency × H × route length

Frequency is trains per hour per direction; the factor 2 counts the two directions. More service hours increase annual carrying capacity at unchanged frequency, as well as train movements and variable operating costs. The frequency optimizer may adjust frequency in response. The allowed daily range is greater than 0 and at most 24 hours.

Target load factor

operations.target_load_factor guides requested frequency. For each service, the evaluator takes the highest one-direction annual segment load L and requests approximately:

required frequency = peak_factor × L / (H × seats × target_load_factor)

The implementation rounds up to configured frequency levels and fits the request within infrastructure limits. This frequency step uses the stock’s seats for one unit; formation size is selected separately afterward.

Enter 65 for a 65% target. Lower targets request more departures for the same demand, potentially reducing waiting time and increasing operating cost. Higher targets request fewer departures, which can increase waiting and crowding. The target must be positive and cannot exceed the maximum load factor.

Maximum load factor

operations.maximum_load_factor caps the modeled annual service capacity:

one-direction annual capacity
= seats × frequency × H × maximum_load_factor × train_units / peak_factor

The evaluator can increase formations up to maximum_train_units, then assigns passengers within segment capacities and attempts alternate paths. Uncarried demand becomes spill.

Enter 85 for an 85% maximum. Increasing this setting permits more passengers at unchanged trains and formation, but it does not improve journey time directly. It must be positive, at most 100%, and no lower than the target load factor.

Conventional fare

rolling_stock.CR.yield_eur_pkm is the conventional rolling stock’s yield in euros per passenger-km. It applies to conventional trains, which run only on conventional infrastructure.

path yield y = Σ(segment length × train-type yield) / Σ(segment length)
OD fare = d_great-circle × y
× [max(d_great-circle, d_min) / fare_reference_km]^(−fare_taper)
annual revenue = Σ(carried annual OD trips × OD fare)

Segment lengths weight the path yield, but the fare’s base distance is the city-pair great-circle distance. With zero taper, a 100 km pair and yield €0.085/passenger-km gives an €8.50 fare.

In the default reference-elasticity model, fares affect revenue and generalized-time metrics; they are excluded from the journey-time elasticity calculation. Raising fares therefore does not directly suppress demand in that model. Financial changes can still alter the network selected by the optimizer.

High-speed fare

rolling_stock.HSR.yield_eur_pkm sets the high-speed rolling stock’s yield in the same formula. At €0.11/passenger-km, a 100 km pair entirely using this yield costs €11 before any taper.

A mixed-service journey uses its distance-weighted train-type yields. Raising this setting can improve high-speed service revenue, but does not directly change its speed, infrastructure construction costs or passenger capacity.

Alternative rail-share model

If you select demand.model = "rail_share" in the JSON, fare does directly affect demand through generalized journey time G:

G = T + fare / value_of_time_eur
rail share = 1 / [1 + exp((G − t0_hours) / sigma_hours)]
Q_potential = 2 × gravity market × rail share

This alternative differs from the default reference-elasticity model. The same fare change can therefore have a different demand effect depending on the selected model.

Reading the results

  • Annual trips: carried passenger journeys across both directions after capacity constraints.
  • Need satisfaction: carried trips divided by eligible need trips. In the elasticity model, connected pairs use modeled journey-dependent demand, and disconnected pairs retain their fixed reference needs in the denominator.
  • Annual net: revenue minus annualized capital, train operating costs, track maintenance and station operating costs. A negative result is a modeled annual deficit.
  • Upfront capital: the sum of infrastructure, station and fleet capital, without annualization.
  • Track length: the sum of active corridor lengths; shared physical infrastructure and the number of parallel tracks are handled separately in cost accounting.

These are uncalibrated scenario estimates. Comparing parameter choices is useful, but the displayed numbers are not forecasts validated against observed demand. A run can finish its iteration limit with incomplete coverage or a capacity shortfall; the status reports that condition.
